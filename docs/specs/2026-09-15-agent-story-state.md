# 小说 Agent：写作、状态更新与撤回规格

日期：2026-09-15。状态：按实机反馈修订；正文以对话楼层交付，资料直接覆盖。实现入口、验证结果和使用限制见 [Agent 交接文档](../agent/README.md)。

## 1. 本阶段要完成的事

让用户用已有世界书、人物卡和开场开始写作，按下面的循环推进：

> 主 Agent 读取设定、开场和当前状态 → 按需委派写作或角色扮演 → 主 Agent 审稿与修改 → 状态 Agent 更新数据库 → 在对话楼层展示完整正文 → 继续下一轮。

用户对最新正文不满意时，可以撤回这一轮，同时撤回数据库更新，再重新写。

主 Agent 决定如何写作、是否委派和何时通过审稿。程序负责保存、工具权限与撤回。用户不用逐人物维护状态，也不用每轮确认一份状态表。

群像叙事、以用户为中心或用户扮演其中一个人物，都由预设和职责提示词表达，共用同一套状态表与写作循环，不增加独立模式或专用社交表。

## 2. 各 Agent 的职责

| 职责 | 工作 |
| --- | --- |
| 主 Agent | 读取资料、把握剧情，按需派发任务，审查正文；满意后调用状态 Agent |
| 正文撰写 Agent | 按委派要求写作或修改正文，将结果交回主 Agent |
| 角色扮演 Agent | 按角色的性格、动机、所知信息和当前处境推演行动／对白 |
| 状态 Agent | 根据主 Agent 审查通过的正文及已有状态，更新世界和人物状态 |

主 Agent 可以自己写，也可以只派发一个写作 Agent；不要求每轮派发所有角色。已有 reviewer 职责仍可按需使用，但本阶段的审稿决定由主 Agent 做出。

状态 Agent 新增为一个固定子职责，复用现有模型与提示词配置；未指定模型时继承主模型。所有子任务继续使用现有的一层 SubAgent、预算、取消和记录机制。

## 3. 一轮如何完成

1. 主 Agent 使用现有会话的世界书、人物卡、预设和用户开场，读取作品最新的动态状态。尚无动态状态时直接从设定和开场开始，不增加初始化向导。
2. 主 Agent 自行写作，或按需要派发正文撰写／角色扮演任务。
3. 主 Agent 检查正文是否符合设定、角色、前文和文风要求；不满意就继续修改。修改稿还不会更新剧情数据库。
4. 主 Agent 选定满意的正式正文，调用一次“根据选定正文更新状态”的工具。应用把选定正文、当前状态表、表格维护规则和必要设定交给状态 Agent。
5. 状态 Agent 通过原生受限工具一次提交本轮各表的行级变化。应用保存正式正文快照、更新前全部状态表的快照和更新后的状态。
6. 选定正文后，应用立即把完整正文放入对应对话楼层，默认折叠这一轮的推理、工具调用和子任务过程。状态待更新或失败时在正文旁明确提示；成功后运行器直接结束本轮，不再调用主模型写总结。下一轮从更新后的状态继续。

这里的“一轮”指一次正文写作及对应的状态更新，不是一次模型或工具调用。一轮内可以多次改稿，但只完成一次状态更新；普通讨论不触发更新。

**状态 Agent 更新成功就完成保存，不再要求主 Agent 复核状态提案、调用第二个接受工具或让用户点击确认。** 应用仍校验参数、绑定正文是否改变及状态是否过期，防止保存不完整或过期的结果。

## 4. 状态表与维护规则

参考「记忆增强表格」的 [表格与维护规则](https://github.com/muyoou/st-memory-enhancement/blob/321571958b28c75af7a83487fb20794aa11c7912/core/table/sheet.js#L238)、[增量修改](https://github.com/muyoou/st-memory-enhancement/blob/321571958b28c75af7a83487fb20794aa11c7912/index.js#L441) 和 [楼层状态关联](https://github.com/muyoou/st-memory-enhancement/blob/321571958b28c75af7a83487fb20794aa11c7912/core/table/sheet.js#L194)。以下是本应用采用的设计；持久化继续使用现有 SQLite。

### 默认三张表

动态状态按作品保存，列名提供结构，单元格保存自然语言。首版内置三张表：

| 表 | 列 | 默认维护方式 |
| --- | --- | --- |
| 场景状态 | 剧情时间／阶段、地点、在场人物、其他世界状态 | 保存当前场景一行；空表时初始化，场景或世界情况变化时更新 |
| 人物动态 | 人物、位置、当前目标、身体与情绪、关系、所知与判断 | 每个人物一行；首次需要持续跟踪时新增，只更新有变化的单元格 |
| 重要经历 | 参与人物、事件简述、时间／地点、持续影响 | 记录需要记住的已发生事件；新增重要经历，保留未被本轮提及的旧经历 |

人物关系、知道／相信／怀疑的内容均用自然语言表达。关系可以指向任意人物，用户扮演的人物也按同样方式记录。稳定性格和背景继续参考人物卡。

首次更新根据设定、开场和通过审查的正文建立有依据的记录，不要求用户先填表，也不增加单独的初始化模型调用。当前状态和重要经历分别记录“现在怎样”与“发生过什么”；它们不能完整替代原文。

本轮记录另存主任务、采用的正式正文和更新前全部状态表的快照，用于查看和撤回；模型无需维护这份记录。

### 每张表的提示词

表格定义包括表名、列名、用途说明，以及初始化、新增、更新、删除的自然语言规则。这些规则指导状态 Agent 判断该记什么，不作为程序自动触发的剧情逻辑。

维护规则作为状态 Agent 的默认提示词内容，复用现有职责提示词配置方式，用户可以调整记录口径。表和列的稳定标识仍由程序定义；首版不增加完整的增删表／列模板编辑器。

例如，人物动态表的默认规则：

```text
说明：记录随剧情变化的人物状态；稳定设定参考人物卡。
初始化：根据设定、开场和正式正文建立已知状态，无依据的内容留空。
新增：出现需要持续跟踪的新人物。
更新：正式正文明确改变状态时，只修改对应单元格。
删除：通常保留人物；离场、失联或死亡通过状态表达。
```

各表共同遵守：

- 只根据已有设定和本轮通过审查的正文更新，不把废稿、推测或未来安排写成已发生事件。
- 作者知道的秘密不等于人物知道；人物相信的谎言不等于客观事实。
- 本轮没有变化的单元格不用重写，未提及的旧信息不要因此删除。
- 世界书和人物卡仍是作者设定，不由状态 Agent 覆盖。

保留每轮采用的正式正文，发现状态有问题时能够回看原文。首版不增加逐事实的证据表、事件关系图或逐段引文校验；状态保存正确不代表模型的理解一定正确，仍需实际写作检验。

### 读取与增量更新

- 读取返回当前全部状态表及状态版本，使用固定的表／列顺序和稳定的行顺序。表、列、行通过稳定标识引用；行标识由程序生成，不能用显示行号识别人物或事件。
- 状态 Agent 将新增行、更新指定单元格、删除行组成一批操作，通过一次原生 Tool Calling 提交。应用在第 6 节的同一个事务内执行全部操作，不逐行提前保存。
- 更新中未提供的单元格保持原值；清空单元格必须显式提交空字符串，删除必须显式指定行。未知表／列、不存在的目标行或不合法参数使整批失败，不能把失败的更新自动改成新增。
- 无变化时也显式提交空操作列表，保存本轮正文关联和撤回快照；没有调用提交工具或工具失败，不算状态更新完成。

复用现有原生工具参数校验，不解析正文中的 `<tableEdit>` 或执行模型生成的 JavaScript。正文撰写与角色扮演职责只读状态，表格维护规则由状态 Agent 使用。

## 5. 用户不满意时撤回

首版提供“撤回最新一轮”。用户可以修改原指令后重新生成：

- 取出这一轮更新前全部状态表的快照，恢复场景、人物和重要经历，包括恢复删除行、移除本轮新增行。
- 这一轮正文标为已撤回，退出当前正文展示；已采用正文快照和运行记录仍可回看；不保存每次改稿版本。
- 原用户输入恢复到输入框供修改，包括首轮的开场内容，不自动重发。
- 本轮开始时记录主会话的输入位置。撤回后，下一次请求使用本轮之前的完整上下文与用户的新指令；撤回轮的正文、工具结果和状态更新不再作为续写输入。
- 原生工具调用与结果以完整轮次保留或排除，不能只删一条消息，留下不完整的工具续接。
- 历史输入查看继续展示当时实际发送的内容，不能因撤回而伪造旧记录。

恢复状态和标记正文撤回一起完成；不让模型根据当前状态“反向推理”如何撤销。使用整轮完整快照，不建立单元格版本系统。本阶段只做这一项撤回操作，不增加指定早期位置的回退、剧情分支或单独的状态更正流程。

## 6. 最少需要的程序保障

这些是保存与撤回本身的实现要求，不增加额外的用户操作：

- **一次保存**：正式正文快照、更新前快照和新状态在一个 SQLite 事务中保存。中途失败全部不生效，不能出现正文已完成但人物只更新一半。
- **绑定输入**：更新任务绑定主 Agent 选定的完整正文和开始时的状态标记；两者变化后拒绝旧结果。同一提交重放只返回原保存结果，已完成轮的不同更新请求被拒绝，不重复更新。
- **受限写入**：只有本次状态 Agent 能提交绑定作品的状态。工具不接受任意 SQL、文件路径或跨作品写入，也不能修改世界书／人物卡。
- **失败与停止**：状态更新成功前失败或停止，保留已生成正文供重试，数据库保持原样；重试状态更新不必重新写正文。成功后即完成本轮，需要回到之前的状态时使用撤回。
- **下一轮**：本轮更新失败时，先重试更新或放弃本轮，再推进下一轮；放弃时排除本轮输入，避免模型把未保存的结果当作已发生剧情。
- **恢复**：重启后读取已经保存的本轮结果和状态，不自动重跑旧写入；保存成功但成功通知丢失，也不能重复更新。

同作品同时只运行一个任务，运行期间不能手动修改资料。状态更新比较绑定正文内容和内部状态标记，拒绝过期结果。模型切换继续遵守原生协议续接边界。

## 7. 上下文与成本

世界书和人物卡每轮采用当前内容，编辑后无需新建会话。每轮开始重建资料前缀，接受编辑造成的缓存失效；一轮内仍追加工具往返，未修改的前缀保持稳定。预设及职责提示词使用选定的模型配置。动态状态按需读取，作为带版本的工具结果追加到后部，不修改早先已发送的状态内容；每次更新返回新版本和变化摘要，不把整份数据库在每次工具往返都重新发送。

状态 Agent 使用当前完整状态表、维护规则、选定正文和必要设定，不继承主 Agent 的全部改稿历史。主 Agent 及其他子任务通过读取最新状态或已返回的变化了解当前剧情，以最新状态版本为准。首版读取不按人物名、关键词或相关性筛选行；发送量和缓存效果通过实际用量观察，不预设命中率。

状态 Agent 的模型调用、用量和停止操作计入现有主子任务体系。

本阶段主 Agent 审稿，因此它可能看到多份候选稿。这一限制先保留，不能为了隐藏它而增加自动新建会话或复杂的上下文整理流程。撤回造成的输入恢复按第 5 节实现。

## 8. 实施与验收

复用 Agent runtime、AgentStore 和 SQLite，增加三张逻辑状态表及维护提示词、状态读写工具、本轮完整快照与最新轮撤回。逻辑表不要求每个作品动态创建 SQL 表。新增数据通过顺序迁移加入，保留已有迁移链和聊天／Agent 数据。

完成标准：

1. 从世界书、人物卡和开场出发，连续写几轮，主 Agent 能按需委派并完成审稿。
2. 首轮无需手工填表即可建立有依据的场景、人物动态和重要经历记录，没有重要经历时允许该表为空；之后按最终正文增量更新，未提供的单元格与旧经历保持原样。
3. 状态 Agent 的请求包含对应表的维护规则；用户可通过职责提示词调整记录口径，通过预设调整群像／用户扮演方式，共用同一套表和循环。
4. 例如“A最终没有告诉B秘密”，状态 Agent 的输入只采用最终正文；真实模型试用检查是否错误记录“B已获知”，以及能否区分误信与客观事实。
5. 行顺序改变不影响稳定标识；非法行／列操作使整批失败，空操作提交仍能完成本轮并撤回。
6. 撤回最新一轮后，三张表的新增、修改、删除全部恢复到之前；下一次输入不再包含该轮内容，可以重新生成。
7. 模拟保存失败、停止、重复提交和重启，验证状态不半写、不重复更新，也不靠模型猜测撤回结果。
8. 完整正文直接显示在对话楼层，无需打开文档面板；整轮过程默认折叠且可展开，工具调用采用紧凑单行标题，错误和状态更新结果 inline 展示。资料编辑的标题、类型和保存按钮固定，仅正文区滚动。
9. 实施时通过相关测试、静态分析及架构门禁，按仓库要求记录日志。真实模型试用单独记录状态遗漏、文风问题、调用量和等待时间，不把模拟测试当成写作质量证明。

## 9. 资料与保存

- 世界书、人物卡、普通文档都直接覆盖同名内容。删除文档版本浏览、版本参数、旧资料冻结和旧稿存储；下轮采用当前资料。
- 模型与规则的同名方案覆盖保存，不保留方案修订历史。不同名称仍可作为不同方案。更换模型需保持原生续接边界，因此有历史时应用模型方案仍新建会话。
- 对话楼层保存审查通过的正文快照，使后续复用同名工作文档不会改写已经发生的剧情。
- 整轮撤回所需的内部快照继续保留：每份文档每轮只记录首次写入前的内容，多次改稿不增加快照。撤回只恢复仍由该轮拥有的写入，用户后来手动编辑的内容不被覆盖。
- schema v18→v19 采用顺序迁移：各文档保留当前有效内容，同名配置方案保留最新内容，正式轮次保留撤回快照；旧的文档修订表被移除。历史调用的实际输入保持原样，仅用于诊断。

## 10. 另记的需求与可选调整

这里仅保留用户提出的方向，不作为本次交付的前置条件：

- **原始需求**：预写剧本按合适时机加载、推进和标记完成；长上下文的隐藏／压缩与缓存效果。
- **检索候选**：以后若考虑 RAG，再一起评估按人物、场景或相关性筛选状态行；本阶段不实现行筛选或 RAG。
- **本次提出的可选调整**：由正文撰写 Agent 再派发审稿 Agent，在子任务内完成修改后，只把最终稿交回主 Agent，以减少主上下文里的多份候选稿。现有 SubAgent 只有一级，这项以后再决定是否实现。
