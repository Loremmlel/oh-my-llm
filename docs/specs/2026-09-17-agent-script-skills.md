# 小说 Agent：Skill 式剧本发现、读取与上下文保留规格

日期：2026-09-17。状态：已实施；用户在规格编写后授权开始实现，具体取舍见第 12 节，验证记录见交接文档。

本文以用户最新要求为准，承接[子任务写作闭环与批量上下文整理规格](2026-09-16-agent-delegation-context.md)。现有实现见 [Agent 交接文档](../agent/README.md)，领域术语见 [CONTEXT.md](../../CONTEXT.md)。

## 1. 产品目标与已确认要求

让主 Agent 在自由 RP 中发现并使用预写剧本。剧本可以描述横跨数周或数月的事件；两次约定事件之间，允许角色互动和其它剧情自然发展。它不是一串必须连续执行的任务，也不默认对应固定数量的正文楼层。

用户已明确：

- 每份剧本以 Markdown 编写，文件开头提供 `name`、`description` 等元信息，采用类似 Skill 的发现与按需读取方式。
- 先向主 Agent 提供元信息，由模型判断是否需要读取；需要时通过工具获得全文，全文追加到当前上下文末尾。
- 会话中新增剧本时，元信息追加到末尾，不回填或改写会话开头的目录。
- 子 Agent 不自动获得剧本元信息或全文。主 Agent 按需把本轮目标、必要信息与限制写入委派描述。
- 剧本中的相对时间与约定事件必须得到尊重。例如“数周后”不代表立即跳过数周，也不代表下一轮就要写对应事件；实际 RP 推进到约定时间时应触发。
- 剧本信息不能因正文隐藏或总结而丢失。

实现以应用侧保留为基础，Harness 提醒为补充。保留范围、运行备忘和首版边界详见第 6、7、12 节；具体实现取舍与用户明确要求分开记录。

## 2. 当前基础与本次范围

### 2.1 已有基础

- 作品内的世界书、人物卡与普通文档；用户保存覆盖当前内容，不提供资料版本浏览。
- 主 Agent 保留连续原生历史，每次新子任务独立组装上下文。
- coordinator → writer → reviewer / state 的写作闭环，以及正式正文保存、失败重试和最新一轮撤回。
- 手动隐藏、总结替代与恢复正式正文；目前只筛选可定位的正式正文块，不裁剪原生工具结果和 Reasoning。
- 剧情状态包含当前故事时间、人物动态和重要经历。

### 2.2 本次拟增加

1. 作者维护的剧本资料及 Markdown 元信息校验。
2. 按会话持久化的元信息发现记录，新增与变化只追加。
3. 主 Agent 专用的按需全文读取工具。
4. 已读剧本与必要运行备忘的上下文保留合同。
5. 主 Agent 根据故事时间安排事件、传达本轮约束的 Harness 规则。
6. 资料编辑、上下文预览与总结管理中的必要说明，以及对应验证。

### 2.3 不在本次范围

- 不开发通用 Skill 插件平台，不执行剧本携带的 Shell、脚本或外部工具。
- 不将剧本强制拆成 Part、TODO 列表、固定楼数任务或自动 DAG。
- 不实现现实时间定时器、后台唤醒、通用小说历法或自然语言时间编译器。
- 不自动把剧本分发给 writer、reviewer、character、state 或 summarizer。
- 不改变既有写作交付闭环，不增加交付后的主模型总结调用。
- 不恢复资料版本系统，不借本功能重写主会话压缩或增加自动固定 N 轮整理。

## 3. 剧本的作者格式与资料边界

### 3.1 Markdown 格式

采用 YAML front matter 加 Markdown 正文。最少要求非空字符串 `name` 和 `description`，正文也须非空。例如：

```markdown
---
name: 秋季校园风波
description: >-
  高一秋季、主角已经加入文学社后可引入。
  事件跨越约两个月；围绕匿名投稿、社团矛盾与校刊出版展开。
---

# 秋季校园风波

## 开端
文学社收到一份匿名投稿。投稿人的身份暂不揭露。

## 数周后
从匿名稿被正式收到之日起数周后，校刊筹备会上出现署名争议。
这之前可以继续课程、日常互动或其它支线，不需要立即推进到筹备会。

## 两个月后
本学期校刊出版时，必须让角色面对署名争议的后果。
具体对白和解决过程可以根据此前 RP 发展，但不能无故消除争议。

## 创作约束
不能把作者已知的投稿人身份直接变成所有角色都知道的事实。
```

`description` 应足以判断何时相关，不只是文学性简介；具体事件、相对时间起点、必须发生的结果、自由发挥空间与结束条件可用自然语言写在正文中。不会要求作者填写程序化日历或每轮任务表。

### 3.2 解析与校验

- 用明确的 YAML 解析器处理 front matter，支持常见的引号字符串、多行 description、UTF-8、BOM 和 CRLF；不以几条正则冒充完整 YAML 解析。
- 缺少 front matter、重复键、错误类型、空名称／描述／正文或超过大小限制时，保存失败并保留用户输入，错误说明应指出修正方法。
- `name` 是作者可读的名称，可使用中文；用于读取的内部 ID 由应用生成。本文借鉴 Skill 的组织方式，不声称符合其全部目录命名、发布和执行规范。
- 首版保证 `name`、`description` 的发现语义。其它 YAML 字段可保留在原文中，但不能自动变成权限、工具定义或程序化触发规则；是否支持额外字段进入目录见第 12 节。
- 沿用普通长文资料的大小保护；正文不因元信息解析而被重新排版或截断。模型读取时获得保存的完整 Markdown，包含 front matter。

### 3.3 所有权

剧本定义归作品所有，同一作品的会话可以发现相同剧本；发现与读取历史归各主会话所有。

作者可以编辑当前剧本。模型只能读取，不能用 `write_document` 创建、覆盖或变更剧本类别；普通文档工具也不能绕过此限制。修改元信息不改变内部 ID，避免改名后误当作全新剧本。

界面名称应与 front matter 的 `name` 保持一致。具体存储可扩展现有资料机制；不要维护两份可互相矛盾的名称，也不要求用户管理真实文件路径。首版至少支持粘贴／编辑完整 Markdown；本地 `.md` 文件导入、导出不是已确认必需项。

## 4. 元信息发现与追加规则

### 4.1 新会话首次请求

主会话尚无历史时，可以在设定之后、历史之前放置初始目录，但必须将其作为本会话首次发现记录持久化，而不是以后每轮重建开头的动态目录。

```text
Harness 与原生工具定义
适用预设
当前世界书、人物卡
初始剧本元信息目录（仅首次建立，后续保持历史位置）
本轮最新剧情状态
本轮用户输入
```

已有历史的会话首次获得本功能时，目录同样追加到现有历史末尾。打开页面、重启应用或重新选择会话都不重新排列已经出现的目录。

### 4.2 新增剧本

用户保存新剧本后，每个会话在下次准备主 Agent 请求时，发现自己尚未见过的剧本并追加元信息通知。首版无需运行中热注入，继续遵守运行中不可编辑资料的既有规则。

```text
原有前缀与连续历史
新增剧本元信息通知
本轮最新剧情状态
本轮用户输入
后续模型回复与工具往返
```

通知最少包含稳定 ID、名称和 description。不携带未读剧本全文，不要求主 Agent 为了发现新剧本再次遍历全文。

### 4.3 修改与移出剧本目录

- 已存在的剧本被修改时，在末尾追加变化通知；既有目录项和工具结果保持原样。
- 仅正文改变、name 和 description 未变时，也必须通知主 Agent“已读旧内容不能继续作为当前剧本使用，使用前重新读取”。
- 通知携带足够的内部内容标识，保证同一变化不会每轮重复追加。内部散列或持久化标识用于一致性，不提供作者版本浏览。
- 若允许将剧本改成其它资料类型，应追加退出目录的通知，并拒绝后续以剧本工具读取该 ID。历史读取仍是历史事实，不自动变成当前有效约束。
- 一次变化在每个会话各通知一次；不能因为另一个会话已经见过就跳过，也不能因为撤回、失败或重启而永久漏通知。

### 4.4 保存与预览

预览和真实请求使用同一组装规则。只打开预览不应将目录标记为已发送；实际输入及相应发现记录要沿用现有运行检查点保存机制，保持一致。

撤回最新一轮继续恢复既有会话历史。用户在轮次之外编辑的剧本定义不随撤回回滚；历史恢复后，仍未通知的当前资料变化应在下一次请求重新追加。

## 5. 按需读取与职责权限

### 5.1 读取工具

建议新增主 Agent 专用工具：

```text
read_script(script_id)
```

工具名称为实现建议，行为合同如下：

- 仅接受当前作品内的剧本稳定 ID；无效 ID、其它作品 ID、非剧本资料和越权职责均显式失败。
- 返回当前名称、内部内容标识及保存的完整 Markdown；不得把内部路径、其它资料或运行环境暴露为读取入口。
- 通过正常原生工具结果追加到当前调用位置，保留合法调用／结果配对。
- 不将全文搬到 Harness、世界书区域或原来的元信息目录位置。
- 同一会话后续请求保留该结果的位置，不每轮重新追加同一份全文。当前内容未变化且全文已在输入中时，Harness 提醒直接使用，避免重复读取。
- 已读取只表示掌握资料，不表示事件已经触发、剧情已经发生或剧本已经完成。

剧本里的自然语言是创作依据，不授予系统权限；未知或恶意字段不能扩大工具能力。

### 5.2 子 Agent 不自动看到剧本

新子任务的上下文组装必须排除剧本目录、全文和主 Agent 的剧本备忘；通用资料列表与读取工具也不能让子任务绕过该边界。

主 Agent 在委派文本中自行提供本轮需要的事实、场景目标、时间范围、必须发生或不得发生的内容以及审查要点。允许按需引用相关原文，但应用不自动附加整个剧本。

writer 继续用 `review_document(name, task)` 派发 reviewer，并在审查描述中传达主 Agent 给出的本轮约束。reviewer 只检查它实际获得的要求，不能声称已核对它没有看到的完整剧本。

state 只把正式正文里已经发生的事情写入剧情状态；未来安排与尚未兑现的约定不能作为人物经历写入数据库。角色推演仍只获得主 Agent 明确提供的信息和已有授权资料。

## 6. 跨时间事件与自由 RP

### 6.1 故事时间优先

剧本推进依据是小说里的时间、阶段与条件，不是现实时间、聊天轮数或模型调用次数。几轮 RP 可以发生在同一天；一轮正文也可能推进数周。

主 Agent 每轮开始时应结合最新剧情状态、保留正文、已读剧本和运行备忘，判断：

1. 哪些剧本现在相关，是否需要读取或重读。
2. 当前处于哪些事件之间，是否可以继续自由互动。
3. 本轮计划的时间跨度是否将到达或越过约定事件。
4. 已发生正文是否已经实现某个约定，以及仍未兑现的内容。

这是一组推理检查，不要求每轮输出报告，也不要求按此顺序派发子 Agent。

### 6.2 相对时间与触发义务

- “数周后”应绑定正文中的实际起点，例如匿名稿收到的日期，而不是工具读取日期、首次出现目录的轮次或用户打开应用的时间。
- 原文只给出模糊时间窗口时，保持其模糊程度；模型可以在合理范围内选择自然的触发时机，但不能擅自将其声明为作者指定的某个精确日期。
- 起点或前置条件尚未发生，不提前推进该事件；条件未满足时也不伪造满足。
- 事件尚未到来时，允许其它剧情，不要求为了“完成剧本”跳时或连续写它。
- 本轮将经过约定时间时，主 Agent 必须在委派中安排相应事件，或限制本轮时间跨度，不能让 writer 无意跳过。
- 如果采用正文意外越过时间点且事件未发生，应明确识别遗漏，结合用户意图修订或使用已有撤回流程；不得把未写出的事情直接补记为已发生。
- 用户的新指令与剧本存在实质冲突时，说明冲突并遵循明确的新指令；不能为了执行旧剧本无视用户改变剧情的要求。

例如，匿名稿在故事中的 9 月初收到，署名争议应在数周后的筹备会发生。中间的课堂、关系变化与其它事件均可自由 RP；主 Agent 不必每轮写争议，但安排进入筹备会或跳转到更晚时间时，必须处理这一约定。

### 6.3 程序保障与模型判断的边界

应用能保证元信息与全文的供给、工具权限、历史保留以及读取内容的一致性。自然语言条件是否满足、剧情是否合理、委派是否遗漏要求，仍由模型判断。

“到点必须触发”是明确的创作要求，不得弱化成可有可无的建议；同时不能把“不压缩全文”或测试通过说成程序已经证明模型绝不漏触发。若以后要求确定性的时间触发，需要另行定义可计算的历法与条件表达，不在本次偷偷引入。

### 6.4 运行备忘

仅保留剧本原文还不足以保留所有执行信息。例如，原文只有“数周后”，而起点发生在哪一天、争议是否已经处理，来自实际 RP；早期正文被总结后，这些锚点也可能丢失。

建议主 Agent 可以维护一份与剧本关联的、简短且不参与正文总结的运行备忘，记录：

- 相对时间对应的实际起点与来源正式正文。
- 已实际发生的相关事件及其时间，不将计划写成事实。
- 仍未兑现的约定、时间窗口和必要条件。
- 当前仍在推进、暂未开始或已经完成的判断，以及简短依据。

备忘以自然语言为主，不强制拆分节点、列出 TODO 或设置每轮截止任务。它不能替代完整剧本，也不能替代剧情状态数据库。

实现采用主 Agent 专用 `record_script_progress(script_id, status, notes, source_round_ids)`，完整覆盖当前会话该剧本的备忘。`status` 为 `planned`／`active`／`completed`，`notes` 为 1–16 KiB；必须先读取当前内容。`active`／`completed` 必须提供本会话已经提交的正式正文 ID，来源不能重复、跨会话或指向未提交正文；`planned` 可无来源，此时只表达未来安排。

主 Agent 可在下一轮开始时核对上一轮结果后记录，不增加交付后的额外模型调用。备忘与原生工具结果在同一个会话检查点保存；撤回恢复轮前的备忘和发现记录。因为实际来源只允许当前会话，撤回来源楼层会同时移除其之后形成的相关判断，不留下其它会话的悬空来源。程序验证来源存在及状态，事实解释仍由模型负责，不能通过随意引用合法 ID 证明说明内容正确。

## 7. 压缩与保留合同

### 7.1 采用应用侧保留

本规格建议：剧本目录通知、读取后的完整原文以及采用后的运行备忘，属于主会话的受保护资料，不参与普通正文隐藏或总结替代。

当前实现只处理正式正文，原生工具结果本来就不被压缩。因此首版应沿用这一机制并增加明确测试，不另造一套通用“特殊消息压缩引擎”。为后续维护保留可识别的类型与来源，不依赖搜索正文里的关键词来识别剧本。

总结 Agent 只获得用户选择的正式正文和既有允许的资料，不把未来剧本交给它混入“已发生剧情摘要”。隐藏 20 楼正文，不能顺带隐藏在这些楼层之间读取的剧本。

### 7.2 Harness 作为补充

Harness 应说明：

- 已读剧本全文在当前会话中保留，直接使用，不因“前文已总结”就例行重读。
- 收到剧本变更通知时，以当前作者定义为准；需要使用时重新读取。
- 当前会话从未读取某剧本、读取失败或输入明确缺少其全文时，先读取再依据其细节安排剧情。
- 正文摘要不等于剧本原文，不能只凭摘要推测未来安排。

不采用“先允许压缩丢掉全文，再在 Harness 里提醒模型想起来时重读”作为唯一保障。模型可能连有这一约定都忘记，无法可靠主动恢复。

### 7.3 缓存和容量

- 元信息变化与全文读取追加在末尾，后续保持历史位置，不反复搬回前面。
- 整理普通正文或编辑世界书仍可能影响缓存；本功能不承诺整个请求一直命中。
- 保护的意思是不被正文整理操作静默删除，不是拥有无限上下文容量。保留较多或较大的已读剧本会占用输入空间。
- 首版可保留所有已经读取的剧本，包括模型认为已经完成的剧本，不自动删除原生工具往返；自动移除已完成剧本不是本规格的默认优化。
- 若达到累计上下文上限，应在发送前明确失败并保留可恢复的数据，不静默截断剧本，也不无限触发压缩／重读循环。
- 只有在另行设计完整的原生往返裁剪和恢复方式后，才考虑清理已完成剧本。运行备忘本身也不能在没有用户约定的情况下自动替代原文。

### 7.4 重启与新会话

同一主会话重启后恢复目录通知、已读全文与可用备忘，历史位置不变。新会话按首次发现处理，不能伪装成已经读取了旧会话中的全文。

作品共享剧情状态，但主会话不共享完整工具历史。如果要在新会话自动接续正在推进的剧本，需要明确可继承的进度及读取规则；这与单纯的 Skill 发现不同，见第 12 节。本文不默认把旧主会话全文复制到新会话。

## 8. 界面与交互

- 在现有资料管理中增加“剧本”类别，复用长文编辑器和保存／取消／未保存退出行为。
- 编辑器清楚展示 front matter 要求，并提供可复制的最小示例；验证失败不关闭窗口，不丢失输入。
- 列表可显示 name 和 description，全文只在编辑或查看时展示；仍应能明确区分世界书、人物卡、剧本与普通文档。
- 用户保存只改变当前定义；是否已经通知某个会话、是否已经被模型读取不能用“保存成功”代替。
- 下一次输入预览展示本次将追加的元信息；历史实际输入仍显示当时发送的原文，不被当前编辑覆盖。
- 总结管理说明“只整理选定正文，已读取的剧本仍保留”，不虚报释放的上下文。
- 不强制增加新侧栏、日历、任务看板或每轮进度弹窗。若采用运行备忘，可在对应剧本查看入口展示，其产品形态待第 12 节确定。
- 沿用 Material、已有布局 token、正文独立滚动和键盘可达行为；验证桌面、窄屏、长 description、解析错误及键盘弹出后的保存操作。

## 9. 实现边界与建议入口

| 现有入口 | 拟承担的变化 |
| --- | --- |
| `lib/features/agent/domain/agent_configuration.dart`、`agent_models.dart` | 剧本资料类别、元信息和稳定身份；必要的纯数据合同 |
| `lib/features/agent/application/agent_context.dart` | 初始发现、会话末尾变化通知、子任务排除与受保护输入组装 |
| `lib/features/agent/application/agent_harness.dart` | 主职责的剧本规则、专用读取工具、委派约束传递要求 |
| `lib/features/agent/application/agent_runtime.dart` | 受限读取、正常工具结果追加、变化发现与检查点一致性 |
| `lib/features/agent/application/agent_workspace_controller.dart` | 编辑保存、下一次输入预览和当前会话刷新 |
| `lib/features/agent/data/`、`application/ports/agent_store.dart` | 资料解析边界、必要的发现记录持久化；如采用备忘则实现对应来源与撤回合同 |
| `lib/features/agent/presentation/agent_documents_panel.dart`、`agent_document_editor.dart`、`agent_summary_dialog.dart` | 剧本资料入口、格式错误及保留范围说明 |

上述为可复用入口，不要求把逻辑全部塞进现有大文件。业务数据模型不导入 Flutter／Riverpod／SQLite；YAML 解析放在合适的输入边界。需要依赖时显式声明，不依赖传递依赖偶然存在。

是否需要 schema 迁移由最终持久化方案决定；如需修改，继续追加顺序迁移并保留已发布历史迁移，不提高最低支持版本。内部一致性标识不构成用户可见的版本系统。

## 10. 验收场景

### 10.1 可自动验证的程序合同

1. 合法中文名称、多行 description、CRLF 和 BOM 能解析；缺字段、错误类型、重复键、空正文及超限输入明确失败且旧资料不变。
2. 新主会话只先收到元信息，没有未读全文；相关工具成功后全文出现在调用位置，原生调用／结果配对完整。
3. 连续会话中新增剧本，旧目录与旧历史保持顺序，新元信息位于原历史之后；下轮不重复通知。
4. 修改 description 或仅修改正文都产生一次变化通知；同一作品另一会话独立发现，重启和预览不造成漏发或重复发。
5. 读取不存在、其它作品或非剧本 ID 失败；子职责不能调用剧本读取或从通用文档工具取得剧本。
6. writer／reviewer 获得主 Agent 明确传达的本轮要求，但不自动获得目录、未来剧本全文或主 Agent 备忘；现有嵌套审查交付仍有效。
7. 在较早正文之间读入剧本，随后隐藏／总结那批正文，原生读取结果及完整剧本仍保留。重启、重新总结和恢复原文不改变此合同。
8. 总结 Agent 的来源中不包含未来剧本；state 不因资料类型扩展而自动获得未发生计划。
9. 撤回后目录发现与当前作者定义正确对齐；失败或中断不伪造成功读取，也不破坏工具续接。若采用运行备忘，撤回其来源正文必须使相关锚点与完成判断退出当前有效输入。
10. 输入达到上限时不静默删减剧本，错误可见，作者资料、正式正文及历史可恢复。
11. 元信息预览与实际发送一致；只查看预览不改变下次发现结果，历史实际输入不随资料编辑变化。
12. 桌面／窄屏能够新增和编辑剧本；解析错误后可修正再保存，未保存退出与同类资料一致，长文本和键盘不遮挡保存入口。

测试所有权遵循仓库规则：解析矩阵归输入边界，追加与选择归上下文，越权和异步一致性归运行器／存储，界面只验证其独有交互；三协议使用共享纯规则，并在协议真实续接边界验证必要代表场景。

### 10.2 真实模型写作验收

使用自建的非用户私有剧本，至少验证：

- 一份横跨两个月的剧本中，模型允许多轮日常 RP，不把“数周后”理解成下一轮或马上跳时。
- 当前时间接近约定事件时，主 Agent 向 writer 明确传达本轮要求，writer 转达相应审查重点。
- 尝试跨过约定日期时，模型安排事件或限制时间跨度，而非直接忽略。
- 早期正文经过总结后，模型仍能读取保留的原剧本，区分未发生约定与已发生剧情；如采用备忘，还应正确使用原时间锚点。
- 新增或编辑剧本后，模型依据末尾通知发现或重读，不机械重复全部读取。
- 已发生内容与预写安排产生冲突时，不通过数据库补写未发生剧情来假装完成。

记录漏触发、误触发、时间漂移、重复读取、委派遗漏、用量及缓存读取的实际表现。模拟测试只证明程序合同，不能代替这些创作质量验收。

## 11. 规格选择的依据

- Skill 的可借鉴部分是名称／描述发现和全文按需加载；注入角色、上下文保留、剧情推进与执行权限由本应用负责，不照搬代码 Agent 的脚本执行能力。[OpenAI 官方 Skill 说明](https://learn.chatgpt.com/docs/build-skills)
- 保持前缀稳定、追加新消息有利于缓存复用，但工具定义、模型配置、缓存边界和有效期也会影响命中；不能仅凭内容相似宣称主子 Agent 共享缓存。[OpenAI 官方缓存说明](https://developers.openai.com/api/docs/guides/prompt-caching)
- 原有正文整理已经保留原生工具结果，优先复用并明确保护合同，避免为“不可压缩剧本”提前建设新的通用上下文系统。

## 12. 首版实施取舍

用户授权开始实现后，采用以下方案；这记录实际实现选择，不将其追写为用户曾逐项指定的需求。

| 项目 | 首版选择 | 能力边界 |
| --- | --- | --- |
| 实际时间锚点与完成记录 | 采用第 6.4 节的受保护运行备忘，关联已提交正文，与检查点及撤回快照一起保存 | 模型仍需主动记录并判断实际时间及完成条件 |
| 备忘在作品内的范围 | 备忘、发现／读取历史归当前主会话，不共享或自动继承 | 新会话重新发现剧本，不承诺接续其它会话的进行中剧本 |
| name、description 之外的元信息 | 只将这两个字段和内部 ID 用于发现；额外 YAML 原样保留 | 不自动解释标签、权限、日历、依赖关系或任意自定义字段 |
| 已完成剧本的上下文清理 | 保留全部已读全文，不裁剪原生工具往返 | 长期累计仍占输入容量，达到现有 4 MiB 上限显式停止 |
| 持久化 | 复用文档表及会话 JSON；发现散列和备忘作为可缺省的新字段，旧会话按空记录读取 | 无新 schema 迁移，不增加资料版本浏览 |
| 编辑与更新 | 名称取自 front matter，编辑使用稳定 ID；正文改变也追加通知，旧备忘退出当前有效记录 | 旧实际输入和原生结果不改写；使用新内容前由主 Agent 重读 |

在运行备忘记录、时间触发判断与委派约束传递上，真实模型的遗漏率需要连续 RP 验证；不能把程序侧的信息保留等同于模型执行质量保证。
